00 / Stage 1 · The problem

What does Stage 1 actually give us?

Picture a brilliant friend with amnesia. Every conversation is wonderful, and every conversation is gone the moment you close the door. That is a plain model API. It can answer, but it cannot remember.

So the first problem is not intelligence. It is continuity. We want to ask a question today, come back tomorrow, and still see the whole exchange.

Why not just keep the messages in the browser?

Because the browser is not yours. Tabs close, devices change, and a refresh would erase everything. Worse, a model reply takes time and can fail partway. We need a place where a half-finished answer can be resumed and a finished one can live forever.

Root cause: conversation state must live somewhere durable, owned by the signed-in user, and reachable from any device. The browser is a viewer, not a vault.

So how do we give the assistant a durable memory?

Two cooperating pieces. The Agent component stores the raw thread: messages, tool calls, and streaming pieces. Our own researchSessions table stores the application’s view of that thread: who owns it, what it is called, and whether it is busy, done, or broken. One string, threadId, ties them together.

AGENT COMPONENT

The conversation itself

Threads, user messages, assistant messages, streamed deltas, and tool activity. We do not hand-roll this; the component is built for exactly this job.

researchSessions

Our view of the conversation

userId, threadId, mode, title, status, and timestamps. This is what the sidebar lists and what authorization checks.

Analogy: the Agent component is the library that stores the books; our researchSessions row is the library card in your name, with a due-date sticker that says “busy” or “finished.”

01 / Stage 1 · Follow one message

How does a message survive a refresh?

  1. You press Send.

    chat.sendMessage verifies the session exists and belongs to you. It also checks the thread ID matches, so you cannot write into someone else’s conversation by guessing an ID.

  2. The prompt is saved before anything else.

    saveMessage writes your words into the Agent thread. Why first? If the model call fails or the browser dies, your question still exists. The scheduler also checks the per-user rate limit here, before we spend anything.

  3. The session is marked busy.

    The status flips to running, and the title is set from your first message (if you had not renamed it). A second message while running is rejected server-side, not just disabled in the UI.

  4. Generation moves to a background action.

    ctx.scheduler.runAfter(0, internal.chat.streamResponse, …) hands the heavy work to an action. Actions can call the model and stream; mutations should stay short and transactional. This is the boundary between “record the request” and “do the expensive thing.”

  5. The reply streams as deltas.

    streamText with saveStreamDeltas writes each chunk of text into the thread as it arrives. The UI subscribes with useUIMessages and folds those deltas into the visible message, so tokens appear live without any WebSocket of our own.

  6. The session is marked done or failed.

    After the stream is consumed, finishResponse patches the status to completed or failed. On reload, the same query returns the persisted messages and the UI looks exactly as you left it.

Send ──→ verify owner ──→ save prompt ──→ status "running" │ └──→ schedule action ──→ stream deltas into thread ──→ status done/failed │ └──→ UI subscribes reactively; refresh re-reads the same persisted thread

Why schedule a separate action instead of streaming inside the mutation?

Convex mutations are transactions: short, deterministic, and rolled back on error. A model call is slow, can fail, and produces side effects. Mixing them would mean a failed generation could erase the saved prompt. Separating them means the record commits first and the expensive work runs safely afterward.

The first-principles takeaway: “streaming” here is not a transport we invented. It is durable state written incrementally, which the UI reads reactively. That is why a refresh mid-answer still shows the partial reply.
02 / Stage 4 · The problem

Why isn’t a single assistant enough for a research report?

One agent with tools can search and answer. So why add complexity? Try asking it to compare broad topic A against broad topic B. It tends to answer the first topic, then the second, in one breath, with shallow evidence for each.

Why does one agent get shallow on a big question?

Because it is doing several different jobs in one pass: decide what to investigate, go investigate, write it up, and check itself. Each job wants a different mindset. Doing them all at once spreads attention thin.

Root cause: “plan, research, write, and verify” are distinct skills. One prompt trying to do all four at once produces a mediocre version of each.

What if we give each job its own agent?

That is the team of Stage 4. Four roles, all using the same configured model, each with one clear instruction:

ROLE 1

Planner

Breaks your question into at most three independent sub-tasks. It returns strict JSON, and invalid output is rejected rather than passed on.

ROLE 2

Researchers

One per sub-task, running in parallel. Each does a web search and a PDF search, then summarizes only the evidence it was handed.

ROLE 3

Writer

Combines the findings into a cited report with inline [n] markers. This is the only role whose output streams to you as a message.

ROLE 4

Fact-checker

Reads the report against the findings and flags unsupported or contradictory claims. It annotates only — it never rewrites or re-researches.

Why keep the other roles’ output out of the chat?

If every internal thought appeared as a chat message, your thread would drown in scratch-work. The plan, findings, and critique go into an researchArtifacts table and appear as a collapsible timeline. Only the finished report joins the conversation. You get a clean thread and a full audit trail.

Analogy: an editor does not print every reporter’s notes in the newspaper. The finished article goes in the paper; the notes live in the newsroom for anyone who wants to check them.
03 / Stage 4 · Follow a research run

What happens when I ask a research question?

A research session is created with mode research. When you send a question, chat.sendMessage notices the mode and hands off to beginResearch instead of the normal single-assistant path.

  1. One run per session, guaranteed.

    beginResearch looks at the newest run for this session. If any run is still active (pending, planning, researching, writing, or verifying), it refuses to start another. Concurrency is enforced by the data, not by trusting the button.

  2. The run is recorded, then the workflow starts.

    A researchRuns row is inserted with status pending and the workflow ID is saved. From here the work continues on the server even if you close the tab.

  3. Planning.

    The Planner returns up to three tasks as parse-checked JSON. The validated plan is stored as a plan artifact.

  4. Researching, in parallel.

    Each task runs its own action concurrently. Each one reserves a search, queries Exa, saves numbered sources, queries the PDFs, then asks the Researcher to summarize the evidence. Findings are stored as finding artifacts. Search calls are capped per run.

  5. Writing.

    Sources are linked to the run, findings are gathered, and the Writer streams the final report directly into your Agent thread. Its full text is also stored as a draft artifact.

  6. Verifying.

    The Fact-checker compares the report to the findings and stores a critique artifact. Then the run and session settle to completed.

question ──→ beginResearch (one active run rule) ──→ workflow │ ├─ plan → plan artifact ├─ research ×N → finding artifacts + sources (parallel, capped) ├─ write → streamed report + draft artifact └─ verify → critique artifact │ └─ run/session → completed | failed | cancelled

Why is the report the only thing streamed to the thread?

Because the report is what you asked for. Everything else is scaffolding. Keeping the scaffolding in artifacts means you can reopen the run later and inspect exactly how the conclusion was reached, without cluttering the conversation.

What does the timeline show?

For a research session the dashboard renders a collapsible timeline with five phases: planning, researching, writing, verifying, completed. Below it, each artifact (plan, findings, draft, critique) opens to show its stored payload. An active run can be cancelled; a failed run can be restarted.

04 / Stage 5 · The problem

Why must the work outlive the browser tab?

Imagine a research run that takes two minutes. You start it, then close the laptop to grab coffee. If the work lived in the page, closing the page would kill it. You would return to nothing.

Why is a normal background action not enough?

A single long action is fragile. If the machine restarts mid-run, or one step throws a transient network error, the whole run is lost with no memory of how far it got. There is no resume point.

Root cause: multi-step work needs a checkpoint after every step, so it can be replayed from where it stopped instead of starting over. That is what makes it “durable.”

How do we get checkpoints without writing them ourselves?

We describe the run as a sequence of steps with the Workflow component. Each step is an ordinary Convex function. The component records each step’s result in a journal, and on a retry it replays the handler and skips the steps that already succeeded. 

run define({ runId })
  advance → planning
  plan        (action, retry on transient failure)
  advance → researching
  research ×N (actions, in parallel via Promise.all)
  advance → writing
  write       (action, no retry — it streams)
  advance → verifying
  verify      (action, retry)

This is also why a run can be cancelled and later restarted from a chosen step: the journal knows what already completed.

What tells the app the run is finished?

When the workflow completes, its onComplete handler runs research.complete. That mutation reads the workflow result and settles both the researchRuns row and the session status. Because the status lives in the database, the UI updates reactively when you reopen the page — no polling loop needed.

Important nuance: the writer step deliberately does not retry. A streamed report is not something we want to silently duplicate. The retry-friendly steps are the ones that are safe to re-run (plan, research, verify).

What stops two research runs colliding?

Two guards. beginResearch refuses to start if an active run already exists, and retryRun refuses to restart if the session is already running. Both are database checks inside mutations, so simultaneous clicks cannot both win.

05 / Stage 6 · The problem

Why is a spending cap surprisingly hard?

Suppose you give each user $5 a month. The obvious plan: before a model call, add up what they have spent; if there is room, make the call; afterward, add the real cost. It sounds fine. It is not.

What goes wrong with “check, then spend”?

Two requests arrive at almost the same moment. Both read “$4.90 spent of $5.00.” Both see about ten cents of room. Both proceed. Now the user has spent past the cap, and the check did nothing to stop it. Multiply that by a burst of parallel research tasks and the overshoot is large.

Root cause: checking and spending are two separate moments. Between them, other requests can slip through the same gap. A correct cap must claim the money before the call, not check it and hope.

What is the smallest fix?

Combine the check and the claim into a single transaction: reserve, then settle. Before a call we estimate its worst-case cost and add it to a “reserved” bucket in the same mutation that verifies there is room. The call runs only if the reservation succeeded. When it finishes, we release the hold and move the real cost into “spent.”

STEP 1 · RESERVE

Claim the maximum up front

One mutation checks spent + reserved + estimate ≤ cap and, if it passes, increases reserved. Because Convex mutations are serializable, simultaneous requests see each other’s holds.

STEP 2 · SETTLE

Move the real cost in after

When the call returns, we subtract the hold and add the actual token-based cost. If the call failed with no usage, we charge the full hold, because a provider may still have billed it.

Why reserve the worst case and not a guess?

Because the whole point is to guarantee we never overspend. If we reserved a small average and the model produced a long answer, the real cost could exceed the hold and cross the cap. Reserving the maximum means a single call can never surprise the budget. The trade-off is the opposite: we may briefly block money that would not actually be spent. Stage 6 chose safety over perfect liquidity.

What is the unit of money here?

Integer nanodollars (one billion per dollar), never floating-point cents. Floats drift when you add thousands of tiny fractions; integers do not. The comparison at the heart of the cap stays exact.

Current limits of this design: the app computes cost from configured per-token prices, not from the gateway’s authoritative bill. The published @convex-dev/ai-budget package was upgraded to its 1.0.0-rc.0 release, but the enforced monthly cap lives in our own ledger. See “What is actually verified” for the honest gap.
06 / Stage 6 · Follow one reservation

What happens around a single chat reply?

  1. Pick a price, or fail closed.

    modelPrice returns USD-per-million-token rates for known models. An unknown model throws instead of being treated as free, so a typo cannot dodge the cap. Rates can be extended with GATEWAY_MODEL_PRICES_JSON.

  2. Reserve the worst case.

    budget.reserve computes estimate = (inputTokens × inputPrice + outputTokens × outputPrice) and tests it against the user’s monthly account. The chat path reserves a deliberately generous ceiling (4,000,000 input and 8,000 output tokens) even though the actual generation is capped at 2,000 output tokens.

  3. If there is no room, stop before the model.

    A failed reservation throws before streamText is ever called. That is the “hard fail before the call” rule: we never start work we cannot pay for.

  4. Run the call through the gateway.

    The model is created with ai.languageModel(ctx, …), which routes the request through the Convex AI Gateway and records it for the budget component’s own audit log and dashboard.

  5. Settle with real usage.

    budget.settle reads the token usage, subtracts the hold, adds the real cost to spent, writes a usageLedger row tagged with the feature, and evaluates alert thresholds.

  6. Alerts fire once per threshold.

    If spending crosses 80% or 100% of the cap, a budgetAlerts row is written — but only if one for that threshold and month does not already exist. A unique index makes “once per period” true even under concurrency.

reserve ──→ spent + reserved + estimate ≤ cap ? ──no──→ fail before the model │ yes │ └──→ model call (gateway, recorded) ──→ settle │ ├─ reserved −= hold ├─ spent += real cost ├─ usageLedger row (feature, tokens, cost) └─ alerts: first crossing per threshold/month

What if a call never reports back?

A hold could otherwise stay forever. A cron job runs every five minutes and settles reservations older than fifteen minutes as “failed,” charging the held maximum. That keeps the cap honest when a run dies without settling.

How do rate limits fit alongside spending limits?

They answer a different question. The budget asks “how much,” the rate limiter asks “how often.” limits.ts defines a fixed window of 30 chat messages per minute and 10 research runs per hour, per user, enforced in sendMessage before anything is saved or spent.

07 / Stage 7 · Operations

How do we run and inspect this thing?

A cap is only useful if a human can see it and adjust it. Stage 7 is the operational layer: who is the admin, how a one-time increase is granted, how a past request is replayed, and what happens when content is deleted.

Who is the admin?

Not a database role. The single deployment variable ADMIN_EMAIL is compared (case-insensitively) against the signed-in user’s email in requireAdmin. Set it, and that account can read cross-user budgets and grant increases; nobody else can. Changing it is a one-line deployment change, which fits the spec’s “single admin” decision.

Granting a one-time increase

At /admin, the admin sees each user’s spent, reserved, and added amounts for the current UTC month, then can add an amount with a reason. The increase is added to increaseNanos, which the reservation check treats as extra headroom on top of the standing cap. Every grant is also written to budgetIncreases with who granted it and why.

Why a ledger row for every increase? Money moved by a human needs a paper trail. The account shows the resulting balance; the increases table shows how it got there.

Replaying a recorded request with another model

The budget component keeps a short-lived audit log of model requests. The dashboard’s replay panel lists the current user’s recent requests, lets them pick a model from the GATEWAY_COMPARISON_MODEL_IDS allowlist, and re-runs the original messages. The comparison is billed to the same user, and the result reports the comparison text, its cost, and its latency.

Why an allowlist and not any model?

Because an arbitrary model could be far more expensive or unsupported. Restricting comparison to an explicit allowlist keeps experimentation inside the operator’s chosen budget envelope.

Deleting a conversation safely

Deleting a session is not just a row delete. The sessions.remove flow cancels any active workflow, deletes the session row, and schedules batched cleanup of documents, chunks, sources, artifacts, and runs. The Agent thread is deleted asynchronously too. Crucially, usage and tool cost rows are kept, so accounting history survives even when content is gone.

Why keep cost history after deleting content?

Because spend already happened. Erasing the conversation should not erase the fact that money was spent, or the monthly cap could be reset by deleting old threads.

The built-in budget dashboard

The budget component ships its own admin dashboard. It is mounted in http.ts with ai.registerRoutes(http) and gated by the AI_BUDGET_DASHBOARD_TOKEN deployment variable. Because the HTML page loads without an auth header, a token is used instead of a user identity check. Without the token configured, the route returns 401.

Operational variables to know

GATEWAY_MODEL_ID (model), EXA_API_KEY (web search), BUDGET_MONTHLY_USD_DEFAULT (the cap; calls fail closed without it), ADMIN_EMAIL (the single admin), GATEWAY_COMPARISON_MODEL_IDS (replay allowlist), and optional knobs for rate limits, task caps, report tokens, and file limits. AI_BUDGET_DASHBOARD_TOKEN gates the built-in dashboard. Email verification is intentionally disabled in auth.ts, which diverges from the full spec.

09 / What is real today?

What is actually verified?

Code can pass checks and still not run. So here is the honest split between “checked mechanically” and “still needs a live run.”

Verified locally and in CI-style checks: pnpm run lint, pnpm run check-types, backend tsc, pnpm run build, and pnpm --filter @convex-research-assistant/backend test (8 tests). The tests cover the UTC month boundary, in-flight reservation math, that two simultaneous holds cannot both enter a budget, that an exhausted budget blocks before a fake model is called, chunk-page overlap, reciprocal-rank fusion, the planner task cap, and that a research run records ordered progress and artifacts.
Verified against Convex Cloud: the functions deploy cleanly to the dev deployment, and the built-in budget dashboard returns 401 without its token and 200 with it.
Not yet verified live: an actual multi-agent research run producing a streamed cited report, a real over-budget rejection against the gateway, and a real cross-model replay. Those need an authenticated browser session and configured provider keys. Do not claim the spec’s acceptance criteria from typechecks alone.
Known gaps and divergences

Email verification is disabled, diverging from spec section 10. Model cost is computed from configured token prices rather than the gateway’s authoritative bill, and the hard cap is enforced by the app’s own ledger rather than the budget component (the published component was an old alpha; it was upgraded to 1.0.0-rc.0). Because the component’s request log is short-lived by default, replay only works while the original request is still retained. A retried research action can reserve and charge again if a provider call succeeded but its artifact commit failed. Image-only PDFs still have no OCR. These are documented in OPERATIONS.md.

One-sentence takeaway: Stage 1 gives the assistant durable memory; Stage 4 gives it a team; Stage 5 makes the team’s work survive interruption; Stage 6 stops it from overspending; and Stage 7 lets a human watch, adjust, and audit the whole thing.
