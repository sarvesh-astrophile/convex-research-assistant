Convex Research Assistant · a first-principles field guide

How did chat learn to research?

Stages 2 and 3 add two kinds of evidence: live websites and your own PDFs. We will start with what goes wrong without them, ask the next natural question, and follow the answer all the way into the code.

00 / Start with the problem

What did Stage 1 already give us?

Imagine a helpful friend who remembers every conversation. Stage 1 gave our assistant that memory: a user signs in, creates a session, sends a question, sees a reply arrive in pieces, and can return to the same thread later.

You ask → save your message → assistant replies → save the reply → reopen later

But memory is not evidence. A remembered conversation cannot tell us what happened on the web this morning or what a brand-new PDF says. The assistant might sound confident even when it has never seen the relevant information.

Root cause: the model can answer from its existing context, but it cannot magically read the live web or a local file that we have not explicitly supplied to it.

So how can we put fresh, checkable information in front of it?

Give it tools: one that fetches web evidence (Stage 2), and one that looks up passages from uploaded PDFs (Stage 3). Both tools feed evidence into the same persistent Agent conversation. A citation then tells the reader where an answer came from.

01 / Stage 2 · Why

Why is “just ask the model” not enough for web questions?

Suppose you ask, “What changed in this week's release?” The model might have been trained before the release. Asking harder does not give it internet access. Even if it guesses correctly, you cannot inspect its evidence.

Why not ask the browser to search and paste everything into the prompt?

That makes the browser decide which sites count, exposes integration details to the frontend, and loses a dependable server-side record of searches and their costs. We want the server to control the search, keep the API key private, and associate results with this question.

Root cause: generation and retrieval are different jobs. Generating fluent text does not fetch facts; fetching facts alone does not explain them. We need a controlled handoff between the two.

What is the smallest useful handoff?

1 / ASK

Assistant chooses a tool

Its instructions say to use webSearch when a question needs current, externally checkable facts. The model passes a short search query; Zod checks that it is 2–500 characters.

2 / FIND

Exa finds evidence

A Convex backend action calls Exa's fast search for up to five results, including highlights. The API key stays in Convex deployment settings, never in the web app.

3 / LABEL

The server numbers sources

It stores each valid web URL, title, and snippet in a sources row. The tool returns entries such as [1] to the assistant, so its reply can refer to the same numbers the UI shows.

4 / EXPLAIN

The answer stays in the thread

The Agent continues generating a reply; its message and tool activity belong to the Agent thread. The separate source rows make evidence easy to show as cards after the response.

Analogy: the model is a journalist, Exa is a librarian, and sources is the journalist's labeled stack of clippings. A polished article without clippings is hard to verify.

02 / Stage 2 · Follow one question

What happens after I press Send?

  1. Save the prompt first.

    chat.sendMessage checks the signed-in user owns the session, saves the user message, marks the session running, and schedules chat.streamResponse. Why first? If the browser closes, the question still exists.

  2. Give the tool a question-specific identity.

    getAssistantAgent(sessionId, promptMessageId) attaches both IDs to its tools. Why two IDs? One identifies the conversation; the other identifies this exact turn, so another answer cannot borrow its sources or search allowance.

  3. Reserve one search call before paying for it.

    search.reserveSearch writes a toolUsage row in a Convex mutation. It rejects a call after RESEARCH_MAX_TASKS calls for this prompt (default 3). Doing the check and write together stops simultaneous tool calls from both passing a separate “check first” step.

  4. Ask Exa for results.

    searchProvider.search is a small interface between our app and Exa. It turns Exa results into a simple shape: title, url, and snippet. Why an interface? If the provider changes, the rest of the assistant does not have to learn a new result format.

  5. Keep the useful evidence.

    search.saveSearch accepts only HTTP(S) URLs, removes URL fragments, deduplicates repeated URLs within the prompt, assigns stable [n] numbers, and updates the usage row with Exa's reported dollar total or a $0.005 fallback estimate.

  6. Write and display.

    The tool hands numbered results to the model. chat.streamResponse streams its reply and stops after at most four model steps. The dashboard loads owned sources reactively and shows clickable web cards below the finished assistant message.

Prompt A ──→ toolUsage (call 1, call 2, … max 3) └──→ sources [1], [2], … ──→ answer: “... [1]” Prompt B ──→ its own usage and its own [1], [2], …

What if Exa fails after the reservation?

The reserved usage row remains with its initial cost of zero; the session response may fail and be marked failed. That row still counts toward the per-question search-call cap. This is a call-count reservation, not the hard monthly spending reservation planned for Stage 6.

03 / Stage 2 · Keep the receipts

Why store sources in a table instead of only in the answer?

A sentence such as “Revenue grew [2]” contains a label, but no URL. If the assistant alone invents that label, the UI cannot know where it should link. Storing a source row gives the label an inspectable record.

Table Important fields Why these fields exist
sources sessionId, promptMessageId, index, kind, title, url, snippet, dedupeKey Connect [n] to one question and one source. kind distinguishes a website from a PDF passage.
toolUsage userId, sessionId, promptMessageId, tool, units, estimatedCostUsd Count Exa calls per prompt, attribute them to a user, and record the reported or estimated tool cost.
researchSessions userId, threadId, status Still owns the conversation and links it to the Agent's thread. Search extends Stage 1 rather than replacing it.

The source-list query first checks session ownership, then uses the sessionId + promptMessageId index. The frontend groups cards with the latest user message ID. The number [1] restarts for each new question, because evidence for question A should not silently become evidence for question B.

Important distinction: the server stores real source rows and tells the model to cite only them. The present implementation does not programmatically check every [n] in generated prose. A displayed marker is an instruction-following result, not proof that every sentence is supported.
04 / Stage 3 · Why

Why can't web search answer questions about my PDF?

A private meeting note or a newly uploaded textbook might not exist on the public web. Exa cannot search a document it has never received. We need a way to store the file and retrieve small relevant passages when the assistant needs them.

Could we simply paste the whole PDF into every question?

That repeats a huge amount of text, wastes model input, may exceed context limits, and makes it difficult to point to the page containing the answer. Think of looking up a recipe: you want the right page, not the whole library on the table every time.

Root cause: documents are larger than a useful answer's context, while questions usually need only a handful of passages. We must prepare the document once and look up the relevant pieces later.

What preparation makes lookup possible?

Upload the original PDF, extract its words page by page, cut the words into overlapping chunks, and make each chunk searchable in two ways: by its words and by its meaning. This is retrieval-augmented generation (RAG): retrieve evidence first, then let the model generate an answer from it.

05 / Stage 3 · Prepare a document

What turns one PDF into searchable evidence?

  1. Ask for permission to upload.

    The dashboard calls documents.uploadUrl. The mutation checks the current user owns the session and has room for another document (default 10). It returns a short-lived Convex storage upload URL.

  2. Store the original file.

    The browser posts the PDF bytes directly to Convex file storage. Why a separate storage ID? A database row should describe a file; it should not contain 25 MiB of binary data.

  3. Attach it to the conversation.

    documents.attach checks ownership again, refuses an already attached storage ID, checks the stored size/content type and filename, writes a documents row, then schedules ingestion. The browser checks a 25 MiB limit too, but the server performs the authoritative metadata check.

  4. Read its pages.

    The Node.js action ingest.process loads stored bytes, checks the %PDF- header, limits pages (default 100), and calls unpdf for page text. An image-only scanned PDF has no text layer, so it fails clearly; this stage has no OCR.

  5. Make passages, with overlap.

    The text is split into windows of 450 words, advancing 380 words each time (70-word overlap). Why overlap? A useful sentence can straddle the boundary between two chunks. Each chunk remembers its starting and ending pages.

  6. Give each passage a meaning fingerprint.

    embedMany sends batches of up to eight passages through the Convex AI Gateway. Each receives a 1,536-number embedding: a numeric representation intended to put similar meanings near each other. Chunks and embedding usage are saved in batches.

  7. Declare it searchable.

    The document moves through extracting → embedding → ready. If extraction or embedding fails, it becomes failed with an error shown beside the file. Retrieval only accepts chunks from ready documents.

PDF file → Convex storage → pages → overlapping chunks ↓ text index + 1,536-number vector index ↓ ready to answer questions

Why keep the original PDF, the document row, and chunks separately?

They answer different questions. Storage holds bytes (“What file was uploaded?”). The documents row holds ownership and progress (“Is it ready?”). documentChunks holds searchable evidence (“Which words on which pages answer this?”). Separate pieces let the UI update progress without rewriting a giant PDF-sized record.

Small but important detail: “450 words” is a word-window choice, not an exact tokenizer. The saved tokenCount is estimated at about 1.4 tokens per word. The spec's 500–800-token target is approximate here.
06 / Stage 3 · Find the right passage

How do we find the right paragraph in a long PDF?

Let's ask: “Where does the handbook describe remote work?” A keyword search is good if the PDF literally says “remote work.” But what if it says “working away from the office”? A meaning-based search may find that passage even without matching words.

Why not use only meaning-based search?

Exact terms matter too: invoice numbers, legal clauses, or a product name may be easiest to find by their literal spelling. Each search method has a blind spot, so we run both.

LIST A / WORDS

Full-text search

A Convex search index ranks chunks containing terms from the question, filtered to the current session. Best for exact names and phrases.

LIST B / MEANING

Vector search

We embed the question using the same gateway model and look for nearby chunk vectors, again filtered to the current session. Best for related wording.

Now we have two ranked lists. How do we combine them fairly?

The raw scores from keyword and vector search mean different things, so adding scores directly would be like adding degrees Celsius to dollars. Instead, use reciprocal-rank fusion (RRF): reward a result for its place in each list. 

score(chunk) = 1 / (60 + keywordRank + 1)
             + 1 / (60 + vectorRank + 1)

If a chunk appears in only one list, it receives only that list's term.
Rank 0 is first place; a smaller rank gives a larger contribution.

For example, passage A ranks first in both lists, so it gets 1/61 + 1/61 ≈ 0.0328. Passage B ranks first in only the keyword list, so it gets 1/61 ≈ 0.0164. A wins because two independent ways of looking found it useful. The constant 60 keeps rank differences gentle rather than letting one lucky first place overwhelm everything else.

A passage near the top of both lists gets two helpful votes. The implementation keeps the best five, checks that their files are ready, stores them as document sources, and gives the assistant a short excerpt plus page numbers. Then it can write “See [2]” while the UI shows “handbook.pdf · p. 4–5.”

Why record the question embedding too? Creating that fingerprint uses a model call. usageLedger records tokens and a provisional cost for both document-chunk embeddings and question embeddings. The default is openai/text-embedding-3-small at 1,536 dimensions; a nonmatching dimension is rejected rather than inserted into an incompatible index.
07 / Put the pieces together

Do we now have two separate assistants?

No. The same Stage 1 Agent thread holds the conversation. Its tool list now includes webSearch and searchDocuments. The model chooses whether to use a tool; the server determines what that tool is allowed to fetch and save. Both kinds of evidence go into the same sources table, with kind telling the UI which card to draw.

User + saved Agent thread │ └── assistant chooses a tool, if needed ├── webSearch → Exa → web source [1] → clickable URL └── searchDocuments → hybrid PDF lookup → PDF source [2] → page range │ └── assistant reply streams into the original Agent thread
Question Stage 2 answer Stage 3 answer
Where is the evidence? On public websites found by Exa. In uploaded PDF passages.
How is it fetched? A backend tool calls the Exa component. A backend tool runs full-text and vector searches.
What does [n] point to? A title, URL, and snippet. A filename, page range, and snippet.
How is usage recorded? toolUsage records Exa search calls. usageLedger records embedding calls.

Ownership starts with the signed-in user's researchSessions row. Public source and document list queries check that row before returning data. The PDF index is filtered by session and hydrated chunks are checked against the same session before becoming citations.

09 / What is real today?

What can we verify, and what still needs a live run?

The code has passed local pnpm run lint, pnpm run check-types, backend TypeScript checking, pnpm run build, and git diff --check. Those checks catch many code mistakes. They do not show that a real Exa search or gateway embedding has succeeded.

Deployment blocker: the Convex deployment did not have EXA_API_KEY set, so convex dev --once rejected the push. Add your Exa key under Convex Dashboard → Settings → Environment Variables, then push with pnpm run dev:server. Never put the key in the frontend or in this HTML file.

How will we know these stages really work?

  1. First check Stage 1.

    Sign in, ask a normal question, watch its reply stream, refresh, and confirm the conversation remains.

  2. Then check Stage 2.

    Ask about a recent public fact. Check that a search actually runs, the answer has [n] markers, cards open real websites, and a toolUsage row is present.

  3. Then check Stage 3.

    Upload a small text-based PDF containing a distinctive fact not on the web. Wait for ready. Ask for that fact and check that the answer cites the right PDF page.

What are the current limits and gaps?

Defaults: three Exa calls per question, five Exa results per call, ten PDFs per session, 25 MiB per PDF, 100 pages, 1,536 embedding dimensions, and five final PDF chunks. The browser uses a fixed 25 MiB check even if the server limit is configured differently. Scanned/image PDFs have no OCR. There is no ingestion retry button, automated citation-to-prose validator, or hard monthly budget enforcement; those are not delivered by these two stages. The embedding cost is provisional (and zero for an unpriced alternative model), not a billing-grade reservation. Email verification remains disabled in auth.ts despite the full spec's requirement.

Which deployment settings matter?

EXA_API_KEY is required to mount the Exa component. Chat also needs GATEWAY_MODEL_ID. PDF embeddings use GATEWAY_EMBEDDING_MODEL (default openai/text-embedding-3-small) and require 1,536 dimensions; GATEWAY_EMBEDDING_DIMS, if set, must be 1536. Optional limit variables are RESEARCH_MAX_TASKS, MAX_DOCS_PER_THREAD, MAX_PDF_BYTES, and MAX_PDF_PAGES. These belong to the Convex deployment, not the browser.

One-sentence takeaway: Stage 1 remembers the conversation; Stage 2 fetches fresh public evidence; Stage 3 makes private PDF evidence findable. Citations connect the answer back to the evidence rather than asking you to trust fluent text alone.
